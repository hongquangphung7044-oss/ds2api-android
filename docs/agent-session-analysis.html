现象

用反代项目（ds2api）接 agent 框架（LangChain / AutoGPT / 酒馆等）时，AI 每次调用完工具后会"开启新对话"，导致模型重新阅读所有上文，甚至重复执行已经做过的动作。

根因

这是 ds2api 的设计选择，不是 DeepSeek 的技术限制。

每次 API 请求，ds2api 都会：

  1. 新建一个 DeepSeek 会话（CreateSession 发空 payload，不接受客户端参数）
  2. 把客户端传来的完整 messages 历史压成单个 prompt 字符串
  3. 用 parent_message_id = 0（作为新会话的第一条消息）发送
  4. 请求结束后主动删除该 session（autoDeleteRemoteSession）

源码证据：

internal/completionruntime/nonstream.go:96-123 — 每次 startCompletionOnce 都 CreateSession
internal/promptcompat/standard_request.go:63-65 — parentMessageID 硬编码为 0
internal/httpapi/openai/chat/handler_chat.go:149-180 — 请求结束即删 session
docs/prompt-compatibility.md:108-113 — 文档明确写明"每次请求新建 chat_session_id + parent_message_id: null"

重复动作的直接原因：第二轮请求时，第一轮的 tool_calls 被渲染成 EPSE XML 文本塞进 prompt 历史，模型重读时可能把历史调用误当作"待执行"的调用。

DeepSeek 其实支持会话延续

上游文档 prompt-compatibility.md:113 明确记载实测结论：

上游实测记录
DeepSeek 远端本身支持同一 chat_session_id 的跨轮次持续对话。2026-04-27 已实测：同一 session 下，第 1 轮返回 response_message_id=2，第 2 轮发送 parent_message_id=2 后成功返回 response_message_id=4。

ds2api 内部也有会话延续能力，但只在单次请求内使用，不跨 API 请求暴露：

  • auto-continue（单次 SSE 流内部续写，最多 8 轮）
  • 空输出重试（复用 session + parent_message_id）
  • expert 模式超长 prompt 分段发送（同 session 发多段）

为什么这么设计

主因：OpenAI 兼容协议的约束

标准 OpenAI ChatCompletions 协议没有让客户端传回 session_id / parent_message_id 的字段，客户端只会发完整 messages 数组。ds2api 选择严格遵守无状态语义，让任意 OpenAI 兼容客户端即插即用。

客观副作用：降低风控关联风险

"用完即删 session"不留可关联的会话痕迹。如果改为长存活 session，DeepSeek 风控能看到"同一会话几秒内连发十几条消息还不等回复"——这是明显的自动化特征。

改进方案评估

方案A：自定义 Header 传回 session（技术可行，风险低）

  • 新增 X-Ds2-Session-Id / X-Ds2-Parent-Message-Id header 解析
  • 已有 X-Ds2-Target-Account 先例
  • 向后兼容：客户端不传则回退原行为
  • 代价：需 agent 框架配合改造

方案B：服务端 session 缓存（不推荐）

  • 按 API Key + messages 指纹复用 session
  • 复杂度高、缓存失效难、多账号并发难处理

方案C：使用 Responses API（已存在）

  • ds2api 已实现 openai-responses surface，原生支持 previous_response_id 会话延续
  • 代价：需 agent 框架切换到 Responses API（酒馆暂不支持，LangChain 较新版本支持）

改进后的效果

维度当前改进后
每轮 prompt 大小完整历史（O(n²) 增长）仅增量（O(n) 增长）
重复动作风险高低（服务端保有会话状态）
单次请求 token高低
响应延迟每轮重读全部上下文只处理增量

一次对话能支撑的轮数

受两个硬约束：

  1. DeepSeek 会话长度上限（不公开，经验约 128K-256K token 上下文窗口）
  2. parent_message_id 链完整性（任何一轮失败/切号，链断裂必须重建）
对话深度可行性
10-20 轮稳定可行
20-50 轮取决于 DeepSeek 会话上限
50+ 轮风险升高，可能被截断
100+ 轮不可行，需新建 session 重发历史
切号会破坏会话链
ds2api 有账号池自动切换，切号后原 session 无法复用，必须新建 + 重发历史。agent 长对话场景切号概率不低，实际收益会打折。

风控影响

降低风险的部分

  • 单次 prompt 变小 → 更像真人短消息
  • 单次请求 token 数降低

升高风险的部分

  • session 跨请求存活 → 长存活会话更易被风控关联分析
  • 同一 session 短时间多次请求 → 自动化特征
  • session 残留 → 需保证用完清理

净风险

场景净风险
短对话（<10轮）+ 单账号略降低
长对话（>20轮）+ 单账号中性
长对话 + 频繁切号升高（切号断链重发历史，比当前更复杂）
agent 高频工具调用可能升高（同 session 连发是明显自动化特征）

结论

核心权衡
改进用"长存活 session"换"小 prompt"，而长存活 session 本身是风控特征。

对 agent 高频工具调用场景，这个权衡可能不划算——省了 token，但 DeepSeek 风控看到的是"同一会话几秒内连续发十几条消息还不等回复"，比"每次新会话发大 prompt"更可疑。

上游选择当前设计，主因是 OpenAI 协议兼容，客观上也有降风控副作用。

务实建议

场景建议
酒馆正常聊天（无工具调用）不改，当前设计够用
agent 工具调用频繁不改，长存活 session 风险 > 收益
agent 工具调用少但对话长可考虑方案A，接受切号断链回退
想省 token控制上下文深度比改会话机制更有效
想避免重复动作在 system prompt 加指示："历史中的 tool_calls 已全部执行完毕，禁止重复调用已执行的工具"
最务实方案
不改 ds2api，用 prompt 工程缓解重复动作，零风险。
